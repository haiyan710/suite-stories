# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Suite Stories" — an internal Slack copilot (two allowlisted users) that researches hotels, ideates experience-led editorial concepts, produces visual directions, and builds versioned static HTML mockups. Python 3.12 + Slack Bolt (Socket Mode) + SQLite, with a pluggable LLM backend: the local Claude Code CLI (`LLM_PROVIDER=claude_cli`, the current setup, runs on the logged-in Claude Team account, no API key) or GLM via Z.ai's Anthropic-compatible API (`LLM_PROVIDER=zai`). Single process, one in-process worker queue — no Redis/broker/microservices, and that is intentional. The bot runs on a MacBook; it only works while that machine and process are up.

## Commands

```bash
python3.12 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m app                                 # run the Slack bot by hand (needs .env); normally launchd runs it, see below
.venv/bin/python scripts/chat_cli.py                    # same pipeline in the terminal, no Slack (uses LLM_PROVIDER)
.venv/bin/python -m pytest tests/ -q                    # all tests (offline: fake LLM provider + fake fetcher)
.venv/bin/python -m pytest tests/test_orchestrator.py -q -k <name>   # single test
ZAI_API_KEY=... .venv/bin/python scripts/run_golden.py              # live golden regression -> data/golden_<ts>.json
```

Live scripts hit the network and cost tokens; unit tests must stay offline. Only one bot may run: `main()` takes an exclusive `data/bot.lock` and a second start exits. Two Socket Mode processes split Slack events between them (stale code answers some requests and they overwrite each other's log).

The bot runs as a launchd agent (`deploy/launchd/com.haiyen.suite-stories-bot.plist`, a template with `__HOME__` / `__PROJECT_DIR__` placeholders, installed with `sed` into `~/Library/LaunchAgents/` as its header comment shows): it starts at login, restarts within 30 s if it exits, runs under `caffeinate -is` so the Mac does not sleep while it is up (on AC power; a closed lid without an external display still sleeps), and logs to `data/bot.log`. After a network change the Socket Mode client can loop on reconnects that break at once (BrokenPipeError) while the process stays up and receives nothing; `SocketWatchdog` counts socket errors and exits the process (when no job is running) after 20 in 10 minutes so launchd restarts it, and the startup catch-up then replays what was missed. After a code change restart it with `launchctl kickstart -k gui/$(id -u)/com.haiyen.suite-stories-bot`; stop it with `launchctl bootout gui/$(id -u)/com.haiyen.suite-stories-bot` (killing the process only makes launchd restart it). Don't start `python -m app` by hand while the agent is loaded — it exits on the lock. `pkill -f "python -m app"` does not match the capitalised macOS binary name. To debug a live run, inspect `data/hotel_agent.db`: `workflow_traces` (per-step specialist/next_action), `sources` (`fetched_ok`, `source_type`), and `projects.research_state` / `concept_state` (JSON). To try a change live without touching the real DB, copy it with sqlite `backup()` and run `chat_cli.py` with `DATABASE_PATH` pointing at the copy.

## Architecture

Request flow: `SlackEventRouter` → `AgentExecutor` (single daemon worker thread, per-thread cancellation, progress messages/reactions) → `EditorialOrchestrator.handle_message` → specialists → SQLite.

- **Progress log**: every specialist step (`_call`) and reply-condensing step emits `step:<label>` (`STEP_PROGRESS_PREFIX`, labels from `_step_label`); the executor posts each as a **new** thread message with elapsed time, then a `Done` line, then the answer. Never edit or delete earlier status messages — users read the thread as a log. Researcher-internal stages (`official`, `coverage`, ...) are not posted.
- **Missed messages**: on start, `catch_up_missed_messages` replays messages from the last `CATCHUP_HOURS` (default 48) in recently active agent threads and their channels through the normal router. Per-message dedup (`slack_events`, key `message:<channel>:<ts>`) makes it idempotent — a message is claimed when routed, so don't start the bot while a dependency it needs (e.g. a Slack scope) is missing, or the replayed message is consumed and never retried.
- **Attachments**: `file_share` messages are accepted; `app/tools/documents.py` downloads files with the bot token (needs the `files:read` scope) and extracts text (HTML/text directly, PDFs via pypdf). Image-only PDFs (slide decks) fall back to `ClaudeCliProvider.transcribe_pdf`, which has Claude read the pages with the Read tool. In a thread with a researched project, `ResearchAgent.ingest_documents` adds them as `verified_official` hotel-supplied evidence (`evidence_level: hotel_document`, 8k-char chunks). Photos embedded in PDFs are extracted to `artifacts/documents/<file_id>/`, captioned one by one by Claude (`ClaudeCliProvider.describe_images`), and stored as research assets with `rights: hotel_supplied`, `private: True` and the deck page's text (`page_context`). Image files (JPG/PNG/TIFF/WebP, up to `MAX_PHOTO_BYTES`, 200 MB for press-kit TIFFs) are `Document(kind="photo")`: downscaled to `artifacts/documents/<file_id>/photo.jpg`, captioned (file name first, then Claude's description) and added as `hotel_supplied` assets like deck photos (`Document.usable`). The editorial brief lists the cleared photos (`_hotel_photo_lines`) so the plan includes moments the layout can illustrate. A message that only shares files is filed and acknowledged (facts/photos added) rather than re-running editorial; a message with an actual request runs it.
- **`app/orchestration/orchestrator.py`** is the only conversational brain. It classifies intent with an LLM call (`prompts/orchestrator.md`), then deterministic overrides (status/workflow/verification questions, pending clarification) can replace it, and `_dispatch` branches on `Intent` (`intents.py`). For substantive work it plans → delegates → inspects → retries, bounded by `MAX_TARGETED_RESEARCH_ROUNDS=2`, `MAX_EDITORIAL_ATTEMPTS=2`, `MAX_VISUAL_REVISION_CYCLES=2`.
  - The research-round budget is shared between the pre-editorial verification loop and Editorial's `needs_research` requests. The pre-editorial loop deliberately uses only `MAX - 1` rounds so Editorial's concrete questions always get one round; don't let it consume the whole budget.
  - A candidate the critic passes with revisions is kept (`revisable`) while the revision pass runs; if that pass breaks before reaching a critic (unparseable or incomplete answer, no direction), `_save_candidate` shortlists the earlier candidate with its revision instructions instead of discarding it. `EditorialAgent` also asks once more for JSON when an answer comes back as prose.
  - Each run gets one extra repair-only editorial pass (beyond `MAX_EDITORIAL_ATTEMPTS`) for a final candidate that is complete in substance but missing required fields. It never grants another creative attempt or critic retry.
- **Specialists** (`app/agents/`): `ResearchAgent` (web evidence only, no concepts), `EditorialAgent` (no browsing), `DesignAgent` (spec, no HTML writes), `BuilderAgent` (writes HTML via `ArtifactManager`), `WriterAgent` (sample drafts), `CriticAgent` (editorial, visual or draft mode). Each has a stable system prompt; the orchestrator passes a per-call typed `SpecialistTaskBrief` (`planning.py`) and typed task/result dataclasses (`handoffs.py`). Keep these role boundaries when adding behaviour.
- **Evidence gating** (`planning.py`): evidence is classified (`verified_official`, `verified_authoritative_secondary`, `corroborated_secondary`, `search_snippet_only`, `inferred`, `unsupported`). Only the first three (`EDITORIAL_ALLOWED_CONFIDENCE`) reach Editorial; a central premise resting on weaker evidence cannot be shortlisted.
- **Provenance is enforced in Python, not by the model**: source ids (S#) are assigned by the app, Sources sections are rendered from the DB (`formatting.py`), and citation checks run on model output.
- **LLM seam**: `app/llm/base.py` defines the `LLMProvider` protocol (`complete`, `complete_with_search`); `build_provider(settings, role=...)` in `app/llm/__init__.py` is the only place one is constructed. Tests inject fake providers — new code should take a provider, never construct one.
  - `claude_cli.py` runs one `claude -p --output-format stream-json` subprocess per call, stripped down (no MCP/skills/settings/session, neutral cwd, only WebSearch for search calls) and with `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN` removed from the child env so it can never switch to API billing (the one sanctioned `os.environ` read outside config). `max_tokens`/`temperature`/`thinking` are ignored. Search grounding comes from WebSearch `tool_result` blocks (`Links: [...]`).
  - `role="research"` gives the researcher `CLAUDE_CLI_RESEARCH_MODEL` (default `claude-sonnet-5-5`); editorial, critic, design and routing use `CLAUDE_CLI_MODEL` (empty = CLI default, Opus). The orchestrator also uses the research provider as its fast model for reply condensation.
  - `zai_glm.py` uses GLM's server-side web search; its quota can run out (see search grounding).
- **Researcher concurrency**: the four initial searches, per-page evidence extraction, per-question follow-up search+fetch, and document chunks run through `ResearchAgent._parallel_map` (`MAX_CONCURRENT_LLM_CALLS`, default 4). DB writes and S# assignment stay sequential and in input order.
- **Sample drafts** (`Intent.WRITE_SAMPLE_DRAFT`, `_draft_flow`; also matched deterministically by `_is_sample_draft_request`): `WriterAgent` drafts from the stored concept, its `outline` and gated research, then the critic QA's it in `DRAFT` mode (`critic_draft.md`) with one revision round. The writer runs on GLM (`build_provider(role="writer")`, `WRITER_PROVIDER=zai`) wrapped in `FallbackProvider`, which switches to Claude on errors, quota or empty answers. **Data rule:** GLM only sees public evidence — if the project has hotel-shared documents (`source_records[].private` / "(shared in Slack)"), `_private_writer` (Claude) writes instead and the reply says so. `[TK: ...]` placeholders are counted from the draft body, not the model's own list. Z.ai silently answers for unknown model ids (with made-up content), so only use ids from its `/v1/models` list. Before each QA round, `WriterAgent.humanize` (prompt `humanizer.md`, adapted from blader/humanizer; runs on the fast Claude model, so private drafts may use it; `HUMANIZE_DRAFTS`, on in `load_settings`, off in the `Settings` dataclass) rewrites the draft once to remove AI-writing tells, in one call that drafts, audits its own rewrite (remaining tells; facts it added) and writes the final version (patterns also from mikiarlo3/ai-copywriter). A rewrite that lists `added_facts` is discarded. The rewrite is discarded unless it keeps every `[TK]`, every `## ` subhead in order and 75-120% of the word count; the critic then checks the rewritten text and flags tells that survived. After the last QA round, `WriterAgent.apply_fixes` (prompt `draft_fixes.md`, fast Claude model) applies its `revision_instructions` (when `PASS_WITH_REVISIONS`) and its `polish` (unless `FAIL`) as exact find/replace edits: an edit is kept only if its passage occurs exactly once and touches no `## ` subhead, instructions needing a rebuild are skipped and listed in the reply, and when any edit was applied the critic re-checks the fixed draft (`critic_draft_final`); if that re-check still finds substantive fixes (not polish alone), one more fix pass and re-check run (`MAX_DRAFT_FIX_ROUNDS=2`, then the remaining fixes are listed). The last re-check's `polish` is then applied once more without a further check (`draft_polish`, the reply says "then N wording edits"), since every re-check finds a little new polish, so the reply's verdict describes the text the team receives (`sample_draft.qa_fixes` records the counts). Distances in drafts come only from `travel_estimates`, never from listings. The draft critic separates substantive fixes (`revision_instructions`: facts, restrictions, travel, required parts, routine framing, AI-tell clusters) from wording `polish` (repeated phrases, idioms, plainer headings); polish alone still gets `PASS`; it is applied by the final fixes pass, and only polish that could not be applied is listed in the reply as optional.
- **Editorial layouts** (`app/artifacts/layout.py`): a draft request mentioning layout/photos/PDF (`_is_layout_request`) also builds a magazine-style page from the draft's `## ` sections. Only `hotel_supplied` photos are used (web images are not cleared); a fast-model call (`layout_images.md`) picks a hero from `_hero_candidates` (large landscape) and one photo per section using the caption and deck page text. Output is one self-contained HTML file (photos embedded as data URIs) uploaded to the thread with `files_upload_v2` (needs `files:write`). Writer art-direction notes (`[IMAGE …]`, `[LAYOUT …]`) are stripped. A layout-only request ("make the layout", not "write a sample draft…") on a thread with a saved `sample_draft` lays out that draft without re-drafting. With no cleared photos the cover is a compact title band (`cover plain`) instead of a full-page dark cover. Every headed section without a photo (except `Insider notes` / `Before you go`) gets an empty photo slot, and a plain cover gets an "Add cover photo" button; `layout_images.md` writes a shot brief for each (`hero_shot`, `shots`, also with an empty catalogue). The page's inline script lets the editor click or drop an image into a slot or the cover, edit captions, and "Save with photos" downloads the page with them embedded; empty slots and the buttons are hidden in print. `artifacts/documents/` and `artifacts/*/layouts/` hold confidential hotel material and are git-ignored.
- **Layout styles** (`app/artifacts/layout_styles.py`): besides the classic template, four styled layouts share the same photo plan: `zigzag` (photo and text side by side, alternating, photo sticky), `image_first` (full-width chapter photos, then one column), `inline` (photos set inside one column, breaking into the margin) and `hybrid` (dark masthead, full-width hero, landscape chapter openers and inline photos). `_layout_styles` reads the request ("side by side", "photos inside the text", "all four layouts", Vietnamese too), else `LAYOUT_STYLE` (`load_settings` default `hybrid`; the `Settings` dataclass keeps `classic` for tests); several styles attach several files. Photos of hotel spaces closed on the trip dates (`concept_state.venues.hotel_spaces`, `_closed_space_photos`) leave the section catalogue and close the page as a "When you come back in the warmer months" strip. `[ASK ...]` notes render in blue.
- **Default deliverable: hotel recommendation + itinerary**: the team needs the case for booking a hotel plus a standard trip plan, not one niche experience. With no trip length in the request, `_trip_nights` falls back to `DEFAULT_TRIP_NIGHTS` (`load_settings` default 3; the `Settings` dataclass default is 0 so hand-built test settings keep the single-experience mode). `_itinerary_instruction` makes the booking case the spine (who it is for, 2-3 verified property-specific reasons) and the critic brief carries `FORMAT: hotel recommendation…` so `critic_editorial.md` judges the reasons and the plan rather than calling a day-by-day plan an amenity sequence. Only an explicit length (`_trip_nights_explicit`) re-runs itinerary research on an itinerary project or overrides a stored concept format in drafts.
- **Audience and voice** (from the booking platform's partner brief, kept out of git): readers are Korean luxury travellers who compare their options closely and book when they can see why a hotel fits the trip; they want practical, property-specific detail a listing leaves out (insider tips, how service works, who it suits). The piece is promotional: no drawbacks (an inconvenience only as a helpful tip). English drafts get translated to Korean, so plain concrete sentences. Headline `place line | Hotel`, one-sentence standfirst, Day 1 info line (check-in/out, room to book, location), timed moments per day, an `## Insider notes` block (Best time / Ask for / Don't miss / Right for). Booking-platform benefits (breakfast for two, credits, upgrades) are never the hotel's offers. These rules live in `writer.md`, `outline.md`, `critic_draft.md`, `critic_editorial.md` and `_itinerary_instruction`.
- **Guest experience research** (`EXPERIENCE_RESEARCH`, on in `load_settings`, off in the `Settings` dataclass for tests): once per project (`_needs_experience_research`: no `guest_report` fact yet), `_experience_research` asks five questions (guest reviews, insider tips, history/stories, peer comparison, Korean `후기`) with `ResearchTask.experience=True`. They use the same guide/press search path as destination questions (review and press hosts first, hotel site last), pages are read with `guest_experience.md` (service / tip / story / comparison / moment, attributed, no complaints, no usernames) and facts get `evidence_level: guest_report`. Editorial uses them for texture, tips and stories, attributed; never alone for hours, prices or a central booking reason. Destination and experience rounds are coverage, so `_run_followup` returns before `_assess_followup_claims` and keeps the open questions (they used to replace `critical_unknowns`, sending the next verification round after restaurants on the hotel's blocked site). A fresh (uncached) research run now also gets the itinerary venue round.
- **Traveller segments**: `_parse_segment` maps a request ("for a honeymoon couple", "cho gia đình") to one of `TRAVELLER_SEGMENTS` (families, couples, 50s-60s slow travel, wellness, design and culture, golf, food-led, from the platform's briefs). Several segments named in one request, or "all traveller groups" / "every kind of traveller" / "tất cả các nhóm", give the `mixed` segment: a shared base and shared meals, with days that split giving each group a labelled lane (`MIXED_LANES`, grandparents get the slower option; 120 min daily transit limit). The segment goes into `_itinerary_instruction`, the venue questions, the critic brief and `format.segment` (`_trip_format`); without one, editorial picks the best-fit type itself. A new segment on an existing itinerary re-runs the venue round. Each segment also carries the activities to favour and the vocabulary of its voice (e.g. couples: romantic, together, first, fresh start); `_segment_format` puts them in `format` with `tone_mix` (about 60% informative, 40% in the traveller's voice), which editorial, outline, writer and the draft critic follow: activities must suit the traveller and each moment is framed as what it means for them, not listed. The outline writes 4-5 `title_options` from different angles and picks `title` by the reader's feeling, a billboard test and whether the promise can be repeated; the reply shows the others. The draft keeps that `title` as its headline (`_pin_headline`, after the writer and humanizer, which drift to weaker ones) unless a QA instruction mentions the headline. Its `opening_hook` (the dinner-table detail from the evidence) opens the draft's intro. The outline's `title` is `place line | Hotel` and its `stay_info` line (check-in/out, room to book, area) opens Day 1; the draft critic asks for both when missing.
- **Itinerary logistics** (`LogisticsAgent`, `app/tools/geo.py`; `LOGISTICS_CHECK`, on in `load_settings`, off in the `Settings` dataclass): free OpenStreetMap services only (the user does not want a card on Google Cloud): Photon geocoding (Nominatim times out from this machine) biased to the hotel and cached in `geo_cache` (schema v6), and OSRM at routing.openstreetmap.de for free-flow car and foot times. One fast-model call (`logistics_extract.md`) lists each day's stops with arrival times; everything else is Python: time-of-day traffic multipliers (`TRAFFIC_BANDS`, 1.4-2.0x at rush hour; the earlier 2.0-3.5x turned an hour-long airport transfer into "110-195 minutes"), car overhead, walk when ≤15 min, dwell time per stop kind, `not_feasible` / `tight` legs against the plan's times, long rides, and a daily transit limit (120 min for couples/slow/wellness, else 180). No rail/boat times and no opening hours (Overpass was unreachable): a leg over `INTERCITY_KM` that the plan makes by train/boat or that starts or ends at a station is listed as unchecked ("use the timetable") instead of a long car ride. It runs before the outline of a shortlisted itinerary (the outline fixes listed issues; the reply gets a "Getting around" section) and, if a concept has none stored, in `_draft_flow`; the writer and draft critic see `outline.travel_estimates` / `travel_fixes`, and `outline.getting_around` is rebuilt from the same check so the critic never quotes a stale summary. Estimates are always written as "about", never as sourced facts.
- **Dinner picks**: the editorial tended to leave itinerary dinners as `[TK]` even when destination research named restaurants. Before an itinerary editorial run, `_dining_picks` sends the gated restaurant facts (catalogue F1..Fn) to the fast model with `dining_picks.md`, keeps a pick only if its name appears in a fact it cites, and `_format_dining_picks` adds them to the editorial brief (`_dining_note`, once per run) for the evenings that dine out; not every evening has to leave the hotel.
- **Near misses**: when the last candidate fails only on central claims the hotel could confirm (`_central_evidence_blockers`), the reply is `_format_near_miss`: the best candidate plus the claims to confirm. A thread message starting `Hotel confirmed:` / `Hotel's reply:` / `Khách sạn xác nhận:` (`_pasted_hotel_reply`) is ingested like a shared document (hotel-supplied evidence) and the editorial re-runs.
- **Trip calendar** (`app/orchestration/calendar.py`): dates are computed in Python, never left to a model (a live run put a holiday on the wrong weekday and every later step copied it). `parse_trip_calendar` reads explicit dates/ranges ("6-10 Feb 2027", "Day 1 Sat 6 Feb … Day 5 Wed 10 Feb") or a Korean holiday plus year (`KOREAN_HOLIDAYS`, Seollal/Chuseok with substitute days; extend it each year from the official calendar); a range fixes the trip length unless an explicit "N-night" disagrees. The calendar (day, date, weekday, holiday and first-Sunday notes) goes into `format.calendar` (stored with the concept), the editorial brief and critic context (`TripCalendar.instruction`), the outline payload, and the writer/critic as `outline.calendar`; it overrides any date in the concept.
- **User amendments**: the extra text of a draft request ("write a sample draft. Keep Day 4 in Rome…", `_amendment_from`) is kept in `concept_state.amendments` and sent as `outline.user_amendments`; writer and critic treat it as overriding the stored concept/outline (the critic used to FAIL a corrected draft for not matching the stale concept). A calendar given in a draft request replaces the stored one. A new shortlisted concept starts with no amendments.
- **Source-free copy, house style and ASK notes**: the reader-facing copy never names its sources ("per the hotel", "one reviewer", "guests describe", publication names; a guide listing such as Michelin may be named): claims become direct recommendations and provenance goes to the writer's `source_notes` (claim → S#, stored on the draft, never shown). House style lives in the `style_rules` table (schema v7, seeded once with the client's first review: no named sources, a why-visit line per place, a dish or ASK per restaurant, and banned phrases). Slack commands, handled before intent classification (`_style_command`): "style rules", "style rule: …", "banned phrase: a | b", "remove style rule #N", "hotel contact: Anna" (per hotel, `contacts` table) and "editor: Minji". Rules and contacts reach the outline, writer and draft critic as `outline.house_style` / `outline.contacts`; banned phrases also feed the deterministic check. Where only the hotel can answer (a dish from the winter menu, a group table) the writer writes `[ASK ANNA: …]` (`[ASK HOTEL: …]` without a contact); the humanizer must keep them, the reply counts them and the layout renders them as blue notes.
- **Stop notes** (`_venue_notes`, prompt `venue_notes.md`; `VENUE_NOTES`, on in `load_settings`, off in the `Settings` dataclass): for an itinerary, one fast call over the gated facts that name the plan's proper names (plus seasonal facts) returns, per outside stop, a why-go `hook`, a `dish`, `closed_days`, booking/fee and night notes, and the hotel's seasonal spaces with `open_on_trip` for the calendar dates. A stop is kept only if its name appears in a fact it cites; stops with no reason to go get one `research_venues` round (destination path) and the notes are redone. Stored as `concept_state.venues`, passed to the outline payload and to writer/critic as `outline.venues`; the deterministic check flags a stop on one of its closed days and a closed hotel space written into the stay instead of as a come-back tip.
- **Deterministic draft checks** (`app/orchestration/draft_checks.py`): after every writer/fix pass `_calendar_fixed` puts each day's real date in its `## Day N` heading and that day's weekday inside its `[TK: …]` notes; after every critic pass `_with_draft_checks` adds what Python can see as revision instructions (a written "Weekday D Month" with the wrong weekday or outside the trip, `BANNED_PHRASES` from config, car times over 150 min outside train/day-trip sentences) and turns a PASS into PASS_WITH_REVISIONS.
- **Multi-day itineraries**: `_parse_trip_nights` reads "4-night" / "4 đêm" / "5 days" from the message. With a trip length, research adds itinerary searches (`search_itinerary_context`), and a venue research round (`_itinerary_research`, six destination questions) runs on cached research or an existing concept. Those questions go out with `ResearchTask.destination=True`, so `ResearchAgent._destination_hits` searches destination guides and press (Michelin, Time Out, tourism boards) instead of the hotel's own site, skips hosts that already failed to fetch for the project, and fetches guide pages first; the hotel-claim verification path (`official hotel brand page` queries, official-first) used to send these to blocked chain sites and return nothing. editorial gets `_itinerary_instruction` (day-by-day, hotel in every day, outside venues only from evidence else `[TK]`), the concept stores `format: {"type": "itinerary", "nights": N}`, and the outline, writer and draft critic switch to one beat/section per day.
- **Research payloads**: research accumulates across runs (hundreds of facts, duplicates). Never slice `json.dumps(research)[:N]` into a prompt — that keeps only the oldest facts. Use `planning.compact_research_json`, which dedupes, puts hotel documents first, then facts naming the distinctive places in its `focus_text` (`focus_names`: proper names from the concept/draft under review that few facts mention), then newest facts, and trims whole facts to a budget. Editorial, critic and writer pass their concept/draft as `focus_text`: with hundreds of cached facts, the critic otherwise never saw the evidence for the restaurants a plan named and ordered them replaced with `[TK]`; `_editorial_outline` adds the same name-matched facts to its evidence. The same applies to whole project state: direct answers use `_answer_context` (concept and latest draft with its `[TK]` list first, research compacted), because research is large and sliced JSON drops everything after it.
- **Search grounding**: `WebSearchTool.search` asks the model to write candidate URLs as JSON, so those URLs/snippets may come from model memory rather than a live search. Z.ai returns its search as `server_tool_use` + `tool_result` blocks (not Anthropic's `web_search_tool_result`); `_parse_response` turns them into `search_results`, or into `LLMResponse.search_error` on failure (e.g. quota exhausted, which the model otherwise hides by answering from memory). `SearchHit.grounded` is true only for URLs in live results, public-index discovery, or user-supplied links. The researcher drops ungrounded candidates that fail to fetch and only uses grounded snippets as `search_snippet_only` evidence. When search failed, the orchestrator appends a visible warning to the reply. Preserve `grounded` when re-typing hits (`dataclasses.replace`, not a new `SearchHit(...)`).
- **Blocked official sites**: many chain sites (marriott.com, ihg.com) return 403 to the fetcher, and some (news.marriott.com) are JS shells that return 200 with no content. Bypassing bot protection is a deliberate non-goal.
- **Keep code property-agnostic**: an early golden test once leaked into runtime code (hardcoded verification queries for one hotel's restaurant). Hotel-specific vocabulary belongs in tests/fixtures, never in `app/`.
- **Verified-fact cache** (`hotel_facts` table, schema v5): every research save (`update_project_state(..., "research")`) upserts the project's editorial-grade facts (confidence in `CACHEABLE_CONFIDENCE`, with source URL/type and the `private` flag) keyed by `hotel_key` (alias-resolved, normalised). A new research thread for a hotel with at least `FACT_CACHE_MIN_FACTS` facts verified within `FACT_CACHE_DAYS` and a public official/brand source skips the initial web research: `_research_from_cache` rebuilds the package with fresh S# per source and marks facts `cached_from` so re-saving does not re-date them (only a fresh extraction re-verifies a fact). "fresh research" / "from scratch" bypasses it; `FACT_CACHE_DAYS=0` disables it. Cached packages carry no photos or experience signals. The 400-fact rebuild reserves shares: property facts first (240), then guest reports (100), then the rest, so cached threads do not re-run guest-experience research. The v4→v5 migration backfills the cache from all stored projects. The DB lock is not re-entrant: never call a locking helper (e.g. `hotel_key` → `resolve_alias`) while holding `self._lock`.
- **Concept memory** (`concepts` table): every shortlisted concept is recorded and the 30 most recent from other projects are passed to editorial and critic (`_memory_payload`) as anti-repetition signals weighted by status (approved/published strong, shortlisted moderate). A stand-alone re-critique updates the lifecycle in both `concept_state` and the memory record (`_apply_critique_status`: FAIL → rejected, a pass revives a rejected concept). Test runs pollute this memory and steer real runs away from the best angles: put `[test]` in a thread's request (`_is_test_marker`, checked in the message and the thread's user history, and kept per project via `project_is_test`) and its concepts are stored with status `test`, which `recent_concepts` skips and `update_concept_status` never changes. Clear older test concepts before real use.
- **Storage** (`app/storage/`): `Database` owns all shared project state (projects, sources, concepts registry used for anti-repetition, design versions, artifact versions, Slack sessions, workflow trace, Slack event dedup). Schema migrations are in-place `ALTER TABLE`s keyed on `SCHEMA_VERSION` in `schema.py` — bump it when changing the schema.
- **Artifacts**: `ArtifactManager` writes append-only `artifacts/<hotel-slug>/vNNN/` versions; "use v1 again" restores by pointer, never by overwriting. Rendering is behind a `Renderer` protocol (default `NoopRenderer` — visual critique reviews source, not screenshots).
- **`app/agent.py` (`HotelResearchAgent`) is deprecated** and not the runtime path, but `AgentCancelled`/`AgentError` are still imported from it by the orchestrator and Slack layer, and several tests exercise it. Don't delete it without moving those.
- `app/slack_dns.py` is a process-local DNS-over-HTTPS fallback used only when the system resolver fails; don't broaden it.

## Prompts are the methodology

Editorial/creative behaviour lives in `app/prompts/*.md`, loaded by name via `load_prompt` (name→file map in `app/prompts/__init__.py`; adding a prompt requires an entry there). Prefer tuning prompts over adding logic for voice/methodology changes. Key rules encoded there: the unit of ideation is a desirable *experience*; a concept fails if swapping the hotel name keeps ~80% of it; no superlatives/"only hotel"/"minutes away" claims beyond evidence; fewer than three directions (including zero) is a valid outcome.

## Conventions

- Default reply is a short conversational English answer; full reports only on explicit "deep research". Other languages only when explicitly requested.
- A shortlisted concept is sent as a compact writing outline, not the full concept: `_editorial_outline` (one fast-model call, prompt `app/prompts/outline.md`) condenses concept + critic notes into title / angle / why readers want it / story outline / proof points / don't claim / check with the hotel, already applying the critic's restrictions; `_format_outline` caps each section so it fits one Slack message. The full concept and critique stay in `concept_state`. If condensation fails it falls back to `_format_editorial`. Critique requests are condensed the same way (`_summarize_critique`, prompt `critique_summary.md`: verdict, ≤3 reasons, ≤3 fixes, next step).
- The bot's Slack avatar source is `assets/slack-avatar.svg` (PNG rendered with headless Chrome); it is uploaded manually in the Slack app's Display Information.
- The workflow trace shown via "show workflow" must not expose private model reasoning.
- All config goes through `app/config.py` `Settings`/`load_settings` — don't read `os.environ` elsewhere. Relative `DATABASE_PATH`/`ARTIFACTS_PATH` resolve against the project root.
- `tests/fixtures/golden_case.json` must contain only the request, scoring criteria (including the `property_terms` / `destination_terms` the evaluator matches), and threshold — never expected answers passed to specialists.
